### 0.2 `dq_ctl.config_change_requests.items` — exact current shape (K2-built; PFP relies on reading it for the candidate sandbox)

PFP `:900` says: "the candidate gets the live effective items plus the CR's items, from `config_change_requests.items`." Confirmed current shape, `dqagent/cp/governance_schema.py:37-43`:

```sql
CREATE TABLE IF NOT EXISTS dq_ctl.config_change_requests(
  cr_id text PRIMARY KEY, state text NOT NULL, author text NOT NULL,
  origin text NOT NULL CHECK (origin IN ('HUMAN','PROPOSER','GENESIS','DEMOTION')), rationale text NOT NULL CHECK (length(rationale) >= 10),
  items jsonb NOT NULL, impact jsonb NOT NULL, base jsonb NOT NULL, loosening boolean NOT NULL,
  approvals_required int NOT NULL CHECK (approvals_required >= 1), signed_hash text NOT NULL,
  signed_rules jsonb NOT NULL, origin_detail jsonb NOT NULL DEFAULT '{}'::jsonb,
  at timestamptz NOT NULL DEFAULT clock_timestamp());
```

`items` is a `jsonb` array of `{artifact_id, kind, op, content[, content_hash]}` objects (confirmed by `dqagent/governance/registry.py:618`, `items = [{**it, "content_hash": _h(it.get("content"))} for it in items]`, and by every TASK_GATE/PIPELINE item literal in `tests/t1/test_pipelines_runtime.py:19-34`). This is exactly the shape PFP's backtest candidate-sandbox construction needs to read: fetch `dq_ctl.config_change_requests.items WHERE cr_id = <CR>` (one row, one column), union that onto the "live effective items" (`dq_ctl.config_effective`, the `DISTINCT ON (artifact_id)` view at `governance_schema.py:128-129`), and apply both into a fresh sandbox control plane the same way `Registry._write_test_genesis`/`gov_apply`'s artifact-insert loop already does (`governance_schema.py:251-254`). **Confirmed**: no new table shape is needed; the existing CR row already carries everything the candidate sandbox needs.

### 0.3 `gov_decide`'s current location, signature, and where the K3 refusal check attaches

Confirmed directly, `dqagent/cp/governance_schema.py:163-200`:
```
163: DROP FUNCTION IF EXISTS dq_ctl.gov_decide(text,text,text,text);
164: CREATE OR REPLACE FUNCTION dq_ctl.gov_decide(p_cr text, p_person text, p_jti text, p_verdict text,
165:   p_explanation jsonb DEFAULT NULL)
166: RETURNS void LANGUAGE plpgsql SECURITY DEFINER SET search_path = pg_catalog, dq_ctl, pg_temp AS $$
```
The function's `p_verdict = 'APPROVED'` branch (`:194-197`) already calls one refusal helper:
```
194:  IF p_verdict = 'APPROVED' THEN
195:    refusal := dq_ctl.promotion_refusal(r.state, r.items, r.origin);
196:    IF refusal IS NOT NULL THEN RAISE EXCEPTION '%', refusal USING ERRCODE = 'check_violation'; END IF;
197:  END IF;
```
`promotion_refusal(p_state, p_items, p_origin)` is defined once, in `dqagent/cp/trace_schema.py:496-554`, and only ever fires for AUTONOMY rank-rise items (confirmed, `:502-503`: `CONTINUE WHEN it->>'kind' <> 'AUTONOMY' OR it->>'op' <> 'PUT'`). PFP's new check — "refuses APPROVE on a CR that changes a TASK_GATE `mode` unless a `cr_evidence` row exists" — is a **different predicate on a different kind**. Two structurally sound options exist, and this is left as a decision (see §4, Decision K3-3): (a) add a second refusal check inline in `gov_decide`'s `:194-197` block, calling a new, separate function (e.g. `dq_ctl.backtest_evidence_refusal(p_cr, p_items)`), parallel to but not merged with `promotion_refusal`; or (b) widen `promotion_refusal` itself to also loop over TASK_GATE `mode`-changing items. Either way, **`gov_apply` needs the identical check at apply time**, exactly as `promotion_refusal` is already re-checked at both `gov_decide:195` and `gov_apply` (confirmed, `governance_schema.py:249`, same function, same reasoning comment: "re-checked at APPLY ... the evidence or record may have changed since the approvals"). The correct anchor for the new check is **both** call sites, not just `:156`/`:164` as PFP's single citation implies.

### 0.4 `run_night` invocation shape, and BACKTEST trace roots — confirmed as new infrastructure, with existing precedent to follow

`run_night(self, data, night_date: str, files: list[Path], *, last: bool, parte: bool = False, drain_passes: int = 3, record: bool = False, person_id: str | None = None) -> dict` is the one definition, `dqagent/runtime.py:1591-1592`, called identically by the full-load path (`dqagent/cli/main.py:82`, `load_synthetic`) and the nightly simulator (`runtime.py:1858`, `sim_run_next`). It always opens a `NIGHT` trace root internally (`runtime.py:1620-1635`, via `tracer.root("NIGHT", tid, ...)`), parented to `tracer.last_run(self.cp, "NIGHT", ...)` when one exists for the same `night_date`.

PFP `:901` says "N runs of `run_night` under BACKTEST roots in each" sandbox. Confirmed: **there is no existing "BACKTEST trace root" concept in the codebase today.** `BACKTEST` is already reserved as a `RUN_KINDS` value (`dqagent/cp/trace_schema.py:18`, `RUN_KINDS = ("NIGHT", "PIPELINE_RUN", "REEVALUATE", "PUBLISH_CYCLE", "DECISION", "APPLY_CHANGE", "BACKTEST", "EXPLAIN", "RECOVER")`) — reserved by K1/K2's own trace-schema work, unused until now — but **zero** call sites of `tracer.root("BACKTEST", ...)` exist anywhere (confirmed by grep: the only hit for the literal string `"BACKTEST"` in any `.py` file is that one `RUN_KINDS` tuple entry). Every other root kind (`NIGHT`, `APPLY_CHANGE`, `PIPELINE_RUN`, `RECOVER`, `DECISION`) follows the same house pattern K1's D6 established and K2b's PIPELINE_RUN root reused (`runtime.py:1730-1732`): mint an id (`tracer.mint(self.cp, f"<PREFIX>-...")`), then `with tracer.root("<KIND>", tid, ..., **self._root_args()):`. **K3's `run_night` calls under BACKTEST roots cannot simply call `self.run_night(...)` as-is**, because `run_night` itself always opens a `NIGHT` root internally (not a `BACKTEST` root) — this is a real shape mismatch PFP's one-line text glosses over, flagged as Decision K3-1 below (does the backtest's own BACKTEST root wrap N nested NIGHT roots as children, or does `run_night` need a parameter to open under a different root kind?).

### 0.5 TASK_GATE `mode`'s current representation, and exactly where `gov_decide` needs the new refusal

Confirmed, `dqagent/cp/governance_schema.py:739`: a TASK_GATE item's `content.mode` is constrained by `gov_item_valid` to `IN ('block', 'hold_until_terminal', 'advisory')`. The genesis-seeded gates use `hold_until_terminal` (confirmed, `docs/blackboard.md`'s K2a entry: "the `w1_dbt` pipeline-id prefix chosen for the two `hold_until_terminal` TASK_GATE names"); the demo's new consumer gate (`tmsis_outbound`) is wired `advisory` (confirmed, `tests/t1/test_pipelines_runtime.py:26-33`, `"mode": mode` with `mode="advisory"` default). `gov_item_lower_only`'s own TASK_GATE branch (`governance_schema.py:916`) already asserts `nw->>'mode' = old->>'mode'` — **a mode CHANGE on an existing TASK_GATE is therefore never lower-only today, and already needs two approvers by construction**, independent of anything K3 adds. K3's new requirement is an ADDITIONAL refusal (the `cr_evidence` check), layered on top of the existing two-person requirement, not a replacement of it. The exact SQL predicate K3 needs to detect "this item changes a TASK_GATE's `mode`" is: `it->>'kind' = 'TASK_GATE' AND it->>'op' = 'PUT' AND (SELECT c.content->>'mode' FROM dq_ctl.config_effective c WHERE c.artifact_id = it->>'artifact_id' AND c.op = 'PUT') IS DISTINCT FROM it->'content'->>'mode'` — this mirrors the existing `old`/`nw` comparison pattern already used throughout `gov_item_lower_only` (e.g. `:905-906`).

### 0.6 "Bound as TEST/test" — confirmed meaning, and the one real gap for a sandbox control plane

The deployment-binding mechanism (`dqagent/deploy.py`, full file read) is **derived in the database from genesis evidence**, never asserted by a caller: `dq_ctl.bind_deployment(p_deployment, p_idp_kind)` (`governance_schema.py:1459` onward — confirmed by grep, not shown in full above but located precisely) looks at whether the control plane holds `TEST-GENESIS` artifacts (→ kind `TEST`, allowing `test`/`demo`) or an applied `GENESIS` change request (→ kind `GOVERNED`, allowing `pilot`/`production`), and refuses any other pairing (`dqagent/runtime.py:283-293`, `_check_deployment`; confirmed by the full suite of `tests/t1/test_deployment_binding.py`, read in full: `test_registry_cannot_prebind_governed_on_fresh_cp`, `test_governed_genesis_binds_inside_gov_apply`, `test_test_genesis_cannot_bind_production`, `test_no_binding_reads_as_production`, `test_binding_carries_the_idp_kind...`, `test_production_needs_oidc_in_the_database`).

"Bound as TEST/test" for a backtest sandbox means: the sandbox control plane runs `dqagent.cp.schema.apply(c)` (same as every fresh test CP, confirmed `tests/t1/conftest.py:20-32`'s `cp_dsn`/`fresh_cp_dsn` fixtures), then a `Runtime(sandbox_dsn, test_genesis=True, deployment="test", ...)` is constructed exactly the way `tests/t1/w1_harness.py:5-8`'s `Slice` class already does (`kw.setdefault("test_genesis", True)`), which internally calls `_test_genesis()` → `write_test_genesis(admin_dsn, state, deployment, idp_kind)` (`registry.py:840-846`) → `bind_deployment("test", "LOCAL")`. **This is existing, exercised infrastructure — not a new mechanism.** The one genuinely new piece is seeding the sandbox's genesis with the CANDIDATE's items (live-effective + CR items) rather than the ordinary genesis seed files (`seed_from_files`, `registry.py:192-221`) — PFP's "base" sandbox presumably gets the live effective items only (unchanged from today's seed), and the "cand" sandbox gets live-effective plus the CR's items layered on top. **Exactly how to seed a TEST genesis with an arbitrary item list, rather than `seed_from_files`'s on-disk YAML, is new code this package must write** — `write_test_genesis`/`_write_test_genesis` (`registry.py:840-862`, confirmed calls `seed_from_files(state)` unconditionally, no parameter to override the item list) does not support this today and needs either a new sibling function or a parameter addition. Flagged as Decision K3-2.

### 0.7 Sandbox control-plane creation/teardown (`dqbt_<cr>_base`/`_cand`) — genuinely new infrastructure, zero precedent

Confirmed by direct search of `dqagent/cp/schema.py` (full file read) and `dqagent/runtime.py`: there is no existing helper anywhere in the tree that creates or drops a throwaway Postgres *database* at runtime (as opposed to a schema or role) outside the test-fixture layer. The only two places `CREATE DATABASE`/`DROP DATABASE` appear are `tests/t1/conftest.py:26,31` (`cp_dsn`/`fresh_cp_dsn` pytest fixtures, test-only) and `dqagent/cli/main.py:122-124` (`cmd_demo`'s own `DROP DATABASE IF EXISTS {db} WITH (FORCE)` / `CREATE DATABASE {db}`, run as the bootstrap admin connection, not inside any reusable function). **K3's sandbox creation/teardown is new, production(-demo)-path code, with the test-fixture pattern as its only precedent** — this package should extract or mirror `conftest.py`'s `CREATE DATABASE`/`DROP DATABASE WITH (FORCE)` pattern into `dqagent/backtest.py` itself (connecting to the `postgres` maintenance database as the bootstrap admin, exactly as `cmd_demo` already does at `cli/main.py:122-124`), not invent a new mechanism. The naming convention `dqbt_<cr>_base`/`dqbt_<cr>_cand` is PFP's own (`EXECUTION_PLAN.md:342`); `<cr>` must be sanitized into a valid Postgres identifier (lowercase, no hyphens — CR ids are `CR-` + 10 hex chars per `registry.py:632`, `"CR-" + uuid.uuid4().hex[:10]`, which already contains a hyphen that is NOT valid unquoted in a bare identifier without care — flagged as Decision K3-4, a literal defect risk if not handled: `dqbt_cr-xxxx_base` is not a bare-identifier-safe database name as-is).

### 0.8 Windows / portable Postgres: can it create new databases and roles on demand?

Confirmed from `run_demo.ps1:1-18` (full header read) and `CLAUDE.md`'s own Environment section: the Windows path is "portable PostgreSQL via `run_demo.ps1` on `127.0.0.1:55432`", with the same binary (`pg_ctl.exe`/`postgres.exe` from the official PostgreSQL 16 binaries zip) that `tests/t1/conftest.py`'s fixtures already use to `CREATE DATABASE`/`DROP DATABASE` successfully on every T1 test run, including on Windows (per the plan's own "the test that proves the backtest never touches the live control plane also runs on Windows in K6" — implying T1-style fixtures already run cross-platform today). **`CREATE DATABASE`/`DROP DATABASE WITH (FORCE)` are both standard Postgres 16 SQL, unprivileged beyond normal `dq_gov`-level connect rights to the `postgres` maintenance database** (confirmed: `cmd_demo`'s own code does exactly this against the same portable instance, `cli/main.py:122-124`, and the project's own demo script runs this path routinely). **No new decision is needed here**: portable Postgres on Windows already supports this exact operation pattern (ad hoc `CREATE`/`DROP DATABASE`), confirmed by existing, working code — not a gap requiring its own resolution.

## 3. Golden-path worked example (the demo moment, traced through the current code)

Demo moments: PFP `:921`, "Backtest the consumer gate over the synthetic nights, then promote it to block with two signatures," corresponding to `EXECUTION_PLAN.md` §5 steps 8 and 9a (the worked table at PFP `:1140-1141`).

1. **Precondition (built by K2, confirmed real):** `tmsis_outbound` is already wired as an `advisory`-mode consumer PIPELINE with two TASK_GATE items (`taskgate:tmsis_outbound:ie_segment`, `taskgate:tmsis_outbound:encounter_header`) gating `bronze.ie_segment` and `bronze.encounter_header`, applied via a two-person CR (confirmed exact mechanism, `tests/t1/test_pipelines_runtime.py:19-38`, `_wire_tmsis_outbound`). A night has already run with this gate in place, producing a real `dq_ctl.gate_checks` row with verdict `PASS` or `WOULD_HOLD` for each task (`runtime.py:1717-1752`, `_pipeline_run`).

2. **Operator runs the CLI**: `dqagent backtest --pipeline tmsis_outbound --cr CR-xxxx --nights 22 --data synthetic/out/w1`, where `CR-xxxx` is a **new, not-yet-decided** change request proposing the gate's `mode` flip from `advisory` to `block` (constructed the same way `_wire_tmsis_outbound` constructs its PIPELINE/TASK_GATE items — a `gov_propose` call with the two TASK_GATE items' `content.mode` changed to `"block"`, everything else unchanged, so `gov_item_lower_only`'s `nw->>'mode' = old->>'mode'` check at `governance_schema.py:916` correctly refuses lower-only treatment and the CR already needs two approvers by construction).

3. **`backtest.py` builds two sandbox control planes**: `dqbt_<sanitized-cr>_base` (schema-applied, TEST-genesis seeded with today's live-effective items only) and `dqbt_<sanitized-cr>_cand` (same, but seeded with live-effective items **plus** `CR-xxxx`'s own items layered on top — PFP `:900`). Both bind `deployment="test"` the same way `Slice`/`_test_genesis` already do (§0.6).

4. **N=22 runs of `run_night`** execute against each sandbox's own `Runtime` instance, over the same `synthetic/out/w1` data, under BACKTEST trace roots (Decision K3-1 resolves the exact root/nesting shape). Inside the `cand` sandbox, the gate's new `mode="block"` means a `WOULD_HOLD` verdict from `harness/gate.py::gate_verdict` should now actually hold the affected units at the given `release_ceiling`, rather than merely being recorded as advisory telemetry — this is the behavioral delta the backtest exists to measure, and it depends on whatever block-mode enforcement K3 adds to the evaluation/publish path (flagged as Decision K3-5: PFP's text names block-mode PROMOTION but is silent on whether `run_night`/`evaluate.py`/`modes.py` need an actual block-mode enforcement branch added in this package, or whether that enforcement already exists latently and K3 only needs to read its effect).

5. **The report** is built comparing `base` vs `cand` per relation (release/hold/pending counts, rule hit-rate deltas, the held-reason histogram, the advisory `gate_checks` would-HOLD count, both trace-shape digests — reusing the exact `_shape()` digest technique already proven in `tests/t1/test_trace_shape.py:60-72` — and `inputs_digest`, a hash of the synthetic data + CR items actually used).

6. **Determinism gate**: the whole N-night run (steps 3-5) executes **twice**, end to end, and the report is stored **only if both runs' digests match exactly** (PFP `:903`). This mirrors `test_trace_shape_digest_stable_across_two_fresh_cps`'s own two-fresh-CP comparison pattern (`test_trace_shape.py:90-99`), applied here to backtest sandboxes instead of the live-shape test.

7. **Both sandboxes are dropped** (`DROP DATABASE ... WITH (FORCE)`, the same statement `conftest.py:31`/`cli/main.py:123` already use), and the report is written to the **live** control plane only through `dq_ctl.backtest_put(...)`, labelled `SYNTHESIZED`.

8. **Tower**: the CR detail pane (`app/governance/[crId]/page.tsx`) shows a new "Backtest" block with the report's headline numbers and a link to `GET /api/v1/backtests/{report_id}`. An approver who tries to approve the mode-flip CR **before** a backtest report exists is refused by the database (`test_mode_promotion_refused_without_report`); after the report exists and is linked via `dq_ctl.cr_evidence`, two different approvers (the existing `gov_decide` author-cannot-approve-own-change and distinct-approver mechanics, already proven by every other two-person CR in this codebase) approve it, and `gov_apply` flips the gate's `mode` to `block` live.

9. **Promote page** (`app/pipelines/[id]/promote/page.tsx`) is the UI entry point for step 2/8 above specifically for the mode-promotion flow (as distinct from the general-purpose CR detail pane, which handles any CR). PFP's text (`:909`) describes this as "step (a)" only — ceiling promotion (step (b), ORCH-1's `release_ceiling`, ties to F-11's second half) is explicitly deferred to P2-5, out of scope for K3.

## 4. Decisions needed (orchestrator/user; NOT resolved here)

**K3-1 (BLOCKING — a build seat cannot safely proceed past this without a default, and the wrong default is expensive: it determines the whole trace shape the backtest's digest-equality check relies on).** PFP `:901` says N runs of `run_night` happen "under BACKTEST roots." But `run_night` (`runtime.py:1591-1635`) unconditionally opens its own `NIGHT` root internally — it has no parameter to open under a caller-supplied root kind or to nest under an existing root of a different kind. Two structurally different resolutions:
  - (a) The backtest driver opens ONE `BACKTEST` root per sandbox (or one for the whole base+cand pair), and the N `NIGHT` roots nest as children underneath it — this requires zero change to `run_night` itself (nesting already works via `tracer.root`'s own default `parent_trace_id = outer.trace_id if outer else None`, confirmed `tracer.py:352-354`), only a wrapping `with tracer.root("BACKTEST", ...): for night in nights: rt.run_night(...)` in `backtest.py`.
  - (b) `run_night` itself needs a new parameter (e.g. `root_kind="NIGHT"`) so each of the N nights is directly a `BACKTEST` root rather than a nested `NIGHT` root — this requires editing `runtime.py`, a file this package's blast-radius table currently marks "read-only reference."
  Option (a) is clearly lower-risk (no edit to a shared, heavily-tested function) and is this architect's read of PFP's literal intent ("runs ... under BACKTEST roots" most naturally reads as "within/beneath," i.e. nested), but PFP's text does not say so explicitly enough to resolve without the orchestrator's sign-off, because it changes what `_shape()`-style digest comparisons actually compare (one BACKTEST root with N NIGHT children vs. N independent BACKTEST roots).

**K3-2 (a build seat can proceed past this with a stated default, but the default should be confirmed).** `write_test_genesis`/`_write_test_genesis` (`registry.py:840-862`) only knows how to seed a sandbox from `seed_from_files`'s on-disk YAML (`registry.py:192-221`) — there is no parameter to inject an arbitrary candidate item list (live-effective + CR items). Default if unconfirmed: add a new sibling function (e.g. `write_sandbox_genesis(admin_dsn, state, items, deployment, idp_kind)`) that mirrors `_write_test_genesis`'s body but takes `items` directly instead of calling `seed_from_files`, rather than overloading `_write_test_genesis` itself (which many existing callers rely on for its current, file-driven behavior).

**K3-3 (a build seat can proceed with a stated default).** Where exactly the new `cr_evidence`-requiring refusal attaches inside `gov_decide`/`gov_apply`: a new, separate function parallel to `promotion_refusal` (this architect's recommended default, because the predicate — "this item changes a TASK_GATE's `mode`" — is unrelated to AUTONOMY rank-rises and conflating the two inside one function's loop body risks an accidental cross-kind interaction), versus widening `promotion_refusal` itself to also loop over TASK_GATE items. Either requires the identical check at both `gov_decide`'s APPROVED branch (`:194-197`) and `gov_apply`'s equivalent point (`:249`), per the existing precedent comment at `:247-248` ("re-checked at APPLY ... the evidence or record may have changed since the approvals").

**K3-4 (a build seat can proceed with a stated default, but it is a real correctness risk if missed).** CR ids are `"CR-" + uuid.uuid4().hex[:10]` (`registry.py:632`) — containing a literal hyphen, which is not valid inside a bare (unquoted) Postgres identifier without quoting, and even quoted, embedding a user-influenced-shaped string directly into a `CREATE DATABASE dqbt_<cr>_base` statement via string formatting is an identifier-injection risk if not parameterized/sanitized carefully (Postgres has no parameterized DDL identifiers; the common safe pattern is `quote_ident()` or a strict allow-list regex check before formatting). Default if unconfirmed: sanitize by stripping the `CR-` prefix and using only the 10 hex characters (`dqbt_<10 lowercase hex>_base`), which are already guaranteed safe by `uuid.uuid4().hex`'s own character set, rather than attempting to quote the full CR id with its hyphen.

**K3-5 (BLOCKING — this determines whether K3 is "measure an existing capability" or "build a missing one," and getting it wrong either gold-plates a backtest-only package with real block-mode enforcement it wasn't asked to build, or ships a backtest that cannot actually show a behavioral delta between base and candidate).** PFP's P1-3/K2 text is explicit that K2 shipped **advisory-only** gate verdicts (`harness/gate.py`'s own docstring, lines 1-21, confirmed: "K2 is advisory-only (block-mode promotion is K3's scope)... the underlying dbt BUILD EXECUTION stays deferred to K3"). PFP's K3 text (`:888`, "P1-4: backtest and the advisory→block promotion") titles the whole package around this promotion, but its numbered steps (`:898-909`) describe only the backtest CLI, the evidence tables, the `gov_decide` refusal, and the promotion CR mechanics — **none of the five numbered steps describe adding actual block-mode enforcement to the evaluation or publish path** (i.e., code that makes a `WOULD_HOLD`-equivalent verdict under `mode="block"` actually hold a unit, as opposed to merely being promotable as a label). Without this, the backtest's "cand" sandbox run is mechanically identical in its outcome counts to the "base" run (the gate's `mode` field changing from `advisory` to `block` has no behavioral effect anywhere in the current codebase — confirmed by grep: `content.get("mode")`/`content["mode"]` is read only by `gov_item_valid`'s CHECK and `gov_item_lower_only`'s unchanged-mode comparison, never by `harness/gate.py`, `runtime.py`'s `_pipeline_run`, or `evaluate.py`/`modes.py`), which would make the backtest's own report numbers (release/hold/pending deltas) trivially zero regardless of the candidate change — a report that cannot do what PFP's demo moment claims ("Backtest the consumer gate over the synthetic nights" implying a *meaningful* delta is measured). This architect's reading is that K3 likely DOES need to add the actual block-mode enforcement branch somewhere in the evaluation/publish path as an in-scope, necessary precondition for the backtest to measure anything real — but PFP's own numbered steps do not say so, and this is exactly the "plan underspecifies something a build seat needs a default for, and no safe default exists" case this brief asks to flag rather than resolve.

**K3-6 (non-blocking; a build seat can proceed with PFP's literal text as the default).** No CLI test is named by PFP for the `backtest` subcommand itself (only `tests/t1/test_backtest.py`'s three tests, whose literal names do not disambiguate "exercises the CLI subcommand" vs. "exercises `backtest.py`'s functions directly"). Default: the build seat may call `backtest.py`'s functions directly in tests (faster, no subprocess), reserving an actual CLI invocation for a smoke-level check only if time allows, consistent with how `tests/t1/test_deployment_binding.py` tests `Runtime`/`registry` directly rather than through `dqagent demo`'s CLI wrapper.

**K3-7 (non-blocking).** PFP `:908` says the CR-detail route "gains `evidence[]`, additively" — the exact shape of each `evidence[]` entry (presumably `{report_id, items_digest, linked_by, at}`, mirroring `cr_evidence`'s own columns) is not specified beyond the column list. Default: mirror `cr_evidence`'s columns 1:1, following the same "flatten the stored row for display" pattern already used for `track_record` at `app.py:1002-1023` (`flat_track_record`).
