## 2. Graph (wireframes 03 and 03b)

### 2.1 Layout: lanes × rows, dependency-free layered SVG
- **Columns are layers:** raw, bronze, silver, gold, outbound. A node's layer comes from the dbt `fqn` or schema, or from regex `layer_rules` declared on the PIPELINE. A node that matches neither is **unlayered** and sits in its own leftmost lane. Layers are never guessed (PARTF_ARCH §1).
- **Rows are pipelines.** Each row label names its harness pipeline, or says "not in harness".
- **Within a layer, sub-ranks** come from the longest path inside the layer. A barycenter ordering on predecessors runs 3–4 sweeps.
- **Deterministic:** the same snapshot always gives the same picture.
- **Renderer:** a dependency-free SVG component, as in the existing `PipelineDag.tsx` precedent. At about 64 nodes it needs no viewport culling. The prototype layout is `ux/_build/build.py: build_dag`, about 120 lines.

### 2.2 Nodes and edges

| Element | Evaluated node (4) | Discovered node (60) |
|---|---|---|
| Border | Solid, 1.8 px | Dashed, muted fill |
| Gate | Shield: amber when holding units, blue when following a parent unit | none |
| Counts | Held pill (warn) and veto-window pill (info, "V2") | none |
| Run glyph | none (units carry the state) | Empty circle: "no run or gate state" |
| Tooltip | "evaluated by the agent, gate bound" | "discovered, not evaluated" |

| Edge | Style |

## 3. Wire a pipeline (wireframe 04, step 4 of 7)

The wizard **builds a change request**; it never writes configuration. It has seven steps.

1. **Source**
   - Choices: dbt manifest (files); Airflow **API**; Airflow **serialised DAG JSON** export.
   - Airflow DAG `.py` files are never accepted, because parsing one means running it.
2. **Connection**
   - Pick a CONNECTION or propose one. Credentials are a reference only (`env://`, `vault://`, `workload://`).
   - Gate styles offered: harness runner exclusion (dbt), sensor plus ShortCircuit (Airflow), manual exit code.
   - **There is no dbt pre-hook option.** DESIGN.md:373 forbids pre-hooks, because a pre-hook error fails the model.
3. **Discover**
   - Nodes with their layer and the *source* of the layer: `fqn demo_estate.bronze`, a schema, or a `layer_rules` pattern.
   - Unmatched nodes are **unlayered**, and the step offers to add a `layer_rules` pattern.
   - Discovery is a preview, never written (`POST /catalog/discover`).
4. **Gate bindings**: datasets to tasks. Two tables:
   - **Datasets the agent can seal:** dataset, layer, layer source, contract, rules, consuming tasks. A dataset without a contract "cannot be gated".
   - **Gate bindings:** task, the datasets it waits on, mode (block / hold_until_terminal / advisory), max wait, on timeout, and the *downstream trigger rules* check.
   - Live checks:
     - any downstream task of a gate whose trigger rule is not `all_success` is an error that blocks the step;
     - unlayered nodes are a warning;
     - every bound dataset has a contract.
   - A callout states feed applicability, for example: NCPDP is not delivered, so the rules are NOT_APPLICABLE and the gate holds nothing until it is.
5. **Dependencies**
   - Edits the HARNESS dependency graph as a whole (WAIT / EALR / LAST RELEASED, binding, max wait, escalation).
   - The order and cycle check is recomputed live on the whole graph (`plan.py`). There is no per-edge artifact.
6. **Impact preview** (server)
   - gates added or removed;
   - validation errors against the latest snapshot;
   - order before and after;
   - **the RELEASE tier for newly bound datasets: L1**;
   - feed applicability.
7. **Submit for approval**
   - **Two people, enforced by the database** for every PIPELINE, CONNECTION and GATE_BINDING item.
   - Origin HUMAN, rationale at least 10 characters, separation of duties.

This settles the approver count with PARTF_ARCH. The red team's fix to C3 makes `gov_propose` compute requires-two in SQL for these kinds. Newly bound datasets start at L1, so wiring never widens what the agent releases on its own.

## 4. Connections (wireframe 10)

- **List:** connection · adapter · base URL or path · auth method (p2) · last test · last discovery with provenance (LIVE / SYNTHESIZED / Planned) · approval.
- **Detail pane:**
  - adapter (and the note "API or serialised JSON only");
  - base URL;
  - auth method;
  - **secret reference** (never a value; a literal is refused);
  - scope;
  - a test-connection checklist: allow-list, token from the reference, read-only role, DAG found. Each step is marked "fixture" when it is replayed;
  - last discovery: snapshot hash, ratified hash, drift link;
  - approval: **any CONNECTION change is loosening and needs two people.**
- **Actions:** Test connection (read-only), Refresh discovery, Propose change.

## 5. Schedules and expected cadence (wireframe 11, Operate › Deliveries)

- **Expected cadence per feed is governed configuration.**
  - Source: `config/state/ZZ/feeds.yaml`, with `cadence: {expected, every}` and `empty_ok`.
  - A change is a CR. Making a feed less frequent is loosening and needs two people.
  - Not-delivered feeds show their reason and NOT_APPLICABLE rules.
- **Open feed items** (MISSING_DELIVERY, EMPTY_DELIVERY) can be acknowledged inline, with a reason. They never hold a batch.
- **Pipeline schedules are read from the orchestrator** and shown read-only, with provenance. The harness pipelines run on delivery at intake; `af_dq_nightly` shows `0 3 * * *` (SYNTHESIZED). Schedules are changed in the orchestrator, and the next discovery picks them up.

## 6. DAG drift (wireframe 12)

- **List:** pipelines with a shape-hash change, Open or Ratified.
- **Detail:**
  - from and to shape hashes, and the connection;
  - an explanation (template, factual);
  - task diff (added / removed / unchanged count);
  - **rename candidates**: same dataset I/O; a suggestion, never applied automatically;
  - **gate bindings affected**: a binding naming a missing task shows **HOLD DRIFT_UNRATIFIED**;
  - a trigger-rule check.
- **Draft CR rail:**
  - "The agent drafted this from metadata only. It cannot submit it. A named person submits it, and its origin is recorded as **PROPOSER**." This matches `gov_propose`, which accepts only HUMAN, PROPOSER or GENESIS origins; there is no PROPOSE_CR action class.
  - Items: re-point the GATE_BINDING task_id; ratified_shape_hash from → to.
  - Approvals: two people, because removing a gated task is loosening.
  - Rationale, Submit as change request, Edit draft.
